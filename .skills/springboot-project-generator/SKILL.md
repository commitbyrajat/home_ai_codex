# Spring Boot Project Generator

## Non-negotiable rules

1. **Always start with** `java --version` and parse the installed Java feature version. Use that version in `pom.xml` (`java.version` and compiler release). Also run `mvn --version` to verify Maven uses a compatible JDK. Never assume the installed version; if Java is absent or unsupported by a current Spring Boot release, stop and explain rather than silently switching JDKs.
2. Inspect `ls ~/.m2/` and, when present, `~/.m2/settings.xml` without printing secrets. Respect existing Maven repository, mirrors, proxies, credentials, and settings. Never recreate or overwrite `.m2`, `settings.xml`, or local repository configuration. Do not add `-Dmaven.repo.local` unless explicitly requested.
3. **Always generate the initial Maven project with this command** (replace only the artifact ID):
   ```bash
   mvn archetype:generate -DartifactId=<name_of_the_application> -DgroupId=com.app.io -B
   ```
   Run it from the desired parent directory. Do not substitute Spring Initializr, a manually created Maven project, or another scaffolder. Check that the target directory does not already exist; never overwrite a project. If archetype generation fails or is ambiguous, diagnose and request direction instead of silently substituting a different command.
	
   Rules:
	 1. Replace ONLY <name> with the application name.
	 2. NEVER add -DarchetypeArtifactId.
	 3. NEVER add -DarchetypeVersion.
	 4. NEVER add -DarchetypeGroupId.
	 6. NEVER add any other arguments.
	 7. NEVER use Maven quickstart explicitly.
	 8. If this command fails, STOP and report the error.
	 9. Do not attempt alternative Maven generation commands.
	 10. Before executing, verify the command matches this template.

4. **Before creating or modifying `pom.xml`, use configured web search tools** to check official current documentation and compatibility for Spring Boot, Spring Boot Maven Plugin, Spring MVC REST controllers, Springdoc, Docker, JUnit, Cucumber, Spotless, Maven Surefire/Failsafe and Java support. If web search is unavailable, stop and explicitly report the blocked requirement; do not pretend to have searched.
5. Use official sources preferentially; record selected versions, compatibility evidence, URLs and search date in `docs/dependency-research.md`. Never invent version numbers, compatibility or successful command output. Do not blindly select the latest version without checking Java compatibility. Prefer Spring Boot's BOM/parent for managed dependencies and avoid unnecessary explicit versions.
6. Edit the generated archetype's `pom.xml` into a valid Spring Boot POM only **after** successful generation and research. Preserve `com.app.io` as group ID and the requested artifact ID. Ensure Spring Boot Maven Plugin is explicitly configured under `<build><plugins>` and executable JAR packaging works; configure its `repackage` goal if required by chosen parent/build. Configure Maven compiler release to detected Java version.
   **POM preservation guard:** For every existing `pom.xml`, including the POM just generated by the archetype, inspect its current contents and modify only the specific XML sections required by the task. Use targeted patches; never recreate, regenerate, replace, or overwrite the entire POM with a template or a freshly constructed document. Preserve unrelated dependencies, plugins, profiles, properties, repositories, comments, ordering, and formatting. Add missing elements within the appropriate existing section rather than replacing that section wholesale. Review the diff after each POM edit and revert unrelated changes before continuing. If a required change cannot be made as a targeted edit, stop and explain the blocker instead of replacing the POM.
7. Generate `@SpringBootApplication` main class under a package rooted at `com.app.io` and a sample `@RestController` with `GET /api/hello`, JSON response and HTTP 200. Keep controller free of unnecessary business logic. Provide a README with run and curl commands.
8. Enable `springdoc-openapi-starter-webmvc-ui` with a version proven compatible with the selected Spring Boot major version. Validate `/v3/api-docs` and `/swagger-ui.html` (or documented redirect). Springdoc 2.x and 3.x are not interchangeable; verify compatibility rather than hardcoding either.
9. Create a secure, reproducible Dockerfile, `.dockerignore`, and documented build/run commands. Use a maintained Java runtime image with the **same Java feature version** as the compiled app; prefer multi-stage/layered builds where justified. Run as a non-root user, use exec-form ENTRYPOINT, and never bake secrets into the image. If using a prebuilt JAR, document `mvn clean verify` and `mvn package` before `docker build`; validate image build and HTTP endpoint when Docker is available.
10. Add real unit tests (JUnit/Jupiter, assertions) and REST/controller integration tests (MockMvc or equivalent compatible with the selected Spring Boot release). Add **Cucumber BDD** with `cucumber-java`, `cucumber-junit-platform-engine`, and `cucumber-spring` if using Spring test context. Use the official Cucumber BOM where appropriate. Provide `src/test/resources/features/hello.feature`, step definitions, and a JUnit Platform suite or an officially supported discovery setup. Ensure Maven Surefire/Failsafe discovers and runs the Cucumber scenarios; do not accept zero executed scenarios as success.
11. Configure `com.diffplug.spotless:spotless-maven-plugin` in `<build><plugins>` using `googleJavaFormat` with `GOOGLE` style and a compatible, researched formatter version. Cover both `src/main/java` and `src/test/java`. Bind `spotless:check` to the Maven verification lifecycle (choose an appropriate phase), and document `mvn spotless:apply` and `mvn spotless:check`. Never claim formatting success without running checks.
12. Research official troubleshooting/verification commands with web search before final validation. Run formatting, compilation, unit tests, BDD tests, package and verification. All tests must pass, and tests must actually execute. Diagnose failures, fix root causes, rerun relevant checks, and finally rerun the full suite. Never skip tests (`-DskipTests`, `-Dmaven.test.skip=true`) to obtain a green build. If blocked by environment/network/tool availability, report **NOT VERIFIED** and the exact failure; never claim success.

## Surgical File Editing Policy

Apply this policy to every existing project file, including files just produced by the Maven archetype. Create complete new files only after confirming the target does not exist. The POM preservation guard in rule 6 remains mandatory.

**Edit the original project files directly.** Do not create agent-managed copies, candidate files, or backups in `/tmp` or another directory for this editing workflow. Show previews in stdout or through the editor's diff view, then apply the authorized change to the original path. A preview alone is not a completed edit. Native in-place tools may use temporary files internally; do not add a separate copy-and-replace workflow around them.

### Scope and tool selection

Before editing, use `rg` to locate the intended section and inspect the surrounding structure. Check the working-tree diff, or retain the original content in the editor/context when Git is unavailable, so existing user edits remain distinguishable from this task's changes. Identify the exact files, nodes, and expected match count. Avoid whole-file regeneration, broad search-and-replace, or replacing entire classes, dependency lists, plugin blocks, or configuration maps to change one item.

Use installed structure-aware tools for structural edits; use an exact-context `apply_patch` for small unique text edits and formats without a suitable structural editor. Do not run every tool on every file.

| Target | Preferred tool and constraints |
| --- | --- |
| Java code | [ast-grep](https://ast-grep.github.io/guide/rewrite-code.html): AST patterns, explicit `--lang java`, concrete file paths, and sufficiently specific receiver/member context. It does not resolve Java symbols/types; inspect ambiguous or overloaded calls before rewriting. |
| Maven XML | [XMLStarlet](https://xmlstar.sourceforge.net/doc/UG/xmlstarlet-ug.html): namespace-aware XPath selection and node updates. Bind `m=http://maven.apache.org/POM/4.0.0`; distinguish root properties, dependencies, dependencyManagement, build/plugins, pluginManagement, and profiles. |
| YAML configuration | [Mike Farah yq v4](https://mikefarah.gitbook.io/yq/commands/evaluate): update the exact key or selected sequence element. Scope multi-document Spring YAML to the intended document/profile and retain all other documents. |
| Repeated syntax templates | [Comby](https://comby.dev/docs/basic-usage): explicit language matcher and file list for balanced-delimiter rewrites when a template is sufficient. It is syntax-aware, not a type-aware refactoring engine; prefer ast-grep for Java AST constraints. |
| Markdown, properties, Dockerfile, small literal changes | Exact-context patches. Do not round-trip `.properties` or mixed-format files through YAML/XML just because a converter exists. |

Check executable identity and local help before relying on flags. Verified on 2026-11-14: `/opt/homebrew/bin/ast-grep` 0.51.2, `xmlstarlet` 1.7.0, Mike Farah `yq` 4.54.3, and `comby` 1.8.1. These are observations, not required pinned versions. Prefer the unambiguous `ast-grep` command over `sg`; other environments may use that name for a different program. Do not assume a Python/jq-based `yq` accepts Mike Farah syntax. If a preferred tool is unavailable, use an equally narrow patch where possible; do not install tools or regenerate the file merely to complete an edit.

### Preview, apply, and preserve

1. **Select before changing.** Inspect the matches and verify their count and surrounding context. Treat zero matches or unexpected multiple matches as a selector problem, not a successful edit. For additions, check whether the node already exists; insert only the missing child under the correct parent and namespace, without duplicating a dependency/plugin or overriding unrelated profiles.
2. **Preview in stdout.** Use ast-grep's rewrite preview, Comby's `-diff`, or pipe XMLStarlet/yq output to `diff -u <original-file> -`. Do not write the preview to a temporary candidate. Never redirect a command's output to its own input path; that can truncate the original before the tool reads it. Single-quote patterns containing `$` or Comby holes to avoid shell expansion.
3. **Review the actual diff.** Preserve unrelated content, comments, ordering, namespaces, document markers, quoting, line endings, and permissions. XMLStarlet `-P` preserves whitespace nodes but does not guarantee identical serialization; yq can also change presentation or comment placement. If a serializer changes unrelated text, use its query results to construct an exact patch against the original instead of accepting the churn. Do not pretty-print, sort, canonicalize, or convert an entire file as an editing shortcut.
4. **Apply directly to the original file.** After checking the preview, use an exact patch against the original path, or the same bounded tool invocation with ast-grep `--update-all`, Comby `-in-place`, XMLStarlet `-L`, or yq `-i` when its serialization satisfies the preservation guard. Perform this application step before reporting completion; do not stop after a dry run. Avoid repository-wide mutation flags without an explicit reviewed file set. No additional user confirmation is required for ordinary edits already authorized by the task.
5. **Verify the result.** Re-query the changed nodes and confirm expected values/counts, syntax, and absence of duplicate entries; inspect the resulting diff again. Use `git diff --check` when available. Run relevant compilation/tests and the existing validation gates. A successful command exit or a parseable file alone does not prove the intended edit occurred. If an edit is wrong, repair only this task's changes; never discard user work with a broad reset/checkout.

The examples below show stdout previews followed by edits to the original paths. Adapt them after inspecting the actual files and review each preview before executing its apply command. The two Java tool examples are alternatives for the same hypothetical rename; choose one and confirm the replacement method exists and has the intended behavior:

```bash
# Java AST rewrite: preview, then apply to the original Java file.
ast-grep run --lang java --pattern 'service.oldName($$$ARGS)' --rewrite 'service.newName($$$ARGS)' src/main/java/com/app/io/Example.java
ast-grep run --lang java --pattern 'service.oldName($$$ARGS)' --rewrite 'service.newName($$$ARGS)' --update-all src/main/java/com/app/io/Example.java

# Template alternative: preview, then apply to the original Java file.
comby 'service.oldName(:[args])' 'service.newName(:[args])' src/main/java/com/app/io/Example.java -matcher .java -diff
comby 'service.oldName(:[args])' 'service.newName(:[args])' src/main/java/com/app/io/Example.java -matcher .java -in-place

# Maven: verify exactly one root Java property before updating it.
xmlstarlet sel -N m=http://maven.apache.org/POM/4.0.0 -t -v 'count(/m:project/m:properties/m:java.version)' pom.xml
# java_feature must contain the Java feature version detected during preflight.
xmlstarlet ed -P -N m=http://maven.apache.org/POM/4.0.0 -u '/m:project/m:properties/m:java.version' -v "$java_feature" pom.xml | diff -u pom.xml -
xmlstarlet ed -P -L -N m=http://maven.apache.org/POM/4.0.0 -u '/m:project/m:properties/m:java.version' -v "$java_feature" pom.xml

# YAML: change only document 0, keeping other profile documents in the output.
# Choose the actual document/profile for the task instead of assuming index 0.
yq eval '(select(documentIndex == 0) | .server.port) = 8081' src/main/resources/application.yml | diff -u src/main/resources/application.yml -
yq eval -i '(select(documentIndex == 0) | .server.port) = 8081' src/main/resources/application.yml
```

`diff` exit status 1 means differences were found; inspect them rather than treating that status as an editor failure. For XML, `xmlstarlet val -w <file>` checks well-formedness, not Maven semantics. For Spring YAML, `yq eval --exit-status 'tag == "!!map"' <file>` checks parsing and mapping shape, not Spring binding or profile correctness. Finish with the relevant Maven/application checks; keep required Spotless formatting distinct from accidental serializer churn and review its changes separately.

## Required workflow

### A. Preflight
- Ask for application name only if not supplied; use a safe Maven artifact ID (lowercase letters, digits, hyphens).
- Execute `java --version`, `mvn --version`, `ls ~/.m2/` and inspect current directory/target collision.
- Check available editing tools with `command -v ast-grep xmlstarlet yq comby`; confirm versions/CLI identities before using the Surgical File Editing Policy.
- Use web search to verify latest **compatible** Spring Boot stable release, Java support, starter coordinates, plugin and test versions, Cucumber JUnit Platform discovery, and Docker best practices.
- Save source links and version decisions in `docs/dependency-research.md` after generation.

### B. Scaffold
Execute exactly:
```bash
mvn archetype:generate -DartifactId=<name_of_the_application> -DgroupId=com.app.io -B
```
Enter the generated directory, inspect its POM and generated sources, and remove or replace incompatible archetype sample classes/tests only after verifying what was created.

### C. Implement
- Follow the Surgical File Editing Policy for every existing file; preview selectors and review narrow diffs before continuing.
- Configure a Spring Boot parent/BOM, `spring-boot-starter-web` or the correct current equivalent, validation only if needed, Springdoc, Spring Boot test starter, Cucumber and JUnit Platform dependencies.
- Configure Spring Boot Maven Plugin, compiler, Surefire/Failsafe as needed, and Spotless. Research changes to starter names across Spring Boot major versions before using them.
- Implement the application, hello controller, unit tests, HTTP integration test, `.feature` file, Cucumber glue/runner and step definitions.
- Provide `application.yml` or `application.properties` with minimal safe defaults; Swagger endpoints should work in the generated demo.
- Add Dockerfile, `.dockerignore`, `.gitignore`, README and dependency research notes.

### D. Validation gates (all required)
Run from the project root:
```bash
mvn spotless:apply
mvn spotless:check
mvn clean verify
```
Inspect Surefire/Failsafe XML reports and confirm positive test counts for JUnit and Cucumber; confirm zero failures/errors/skips unless skips are explicitly justified. Check the JAR is executable (`java -jar target/<actual-built-jar>.jar`) and use curl to verify `/api/hello`, `/v3/api-docs`, and Swagger UI. Avoid indefinite background processes; clean up launched app processes. If Docker is installed and daemon available, run `docker build` and a container smoke test; otherwise report Docker verification as not run. Never suppress failures.

### E. Failure recovery
- If dependency resolution fails: inspect existing Maven settings, repository availability and researched artifact coordinates; do not rewrite `.m2`.
- If Java incompatibility occurs: recheck `java --version`, `mvn --version`, compiler release, Spring Boot support, and formatter requirements.
- If Cucumber reports 0 tests: inspect suite discovery, feature paths, glue package, JUnit Platform engine and Surefire versions; fix and rerun.
- If Spotless fails: run `mvn spotless:apply` and rerun check and full verify.
- If runtime/Swagger fails: inspect startup logs, selected springdoc compatibility and mappings; fix and rerun smoke tests.
- If tests fail: fix implementation or test assumptions; do not delete tests or weaken assertions just to pass.

## Deliverables and completion report
Report project path, installed Java and Maven versions, chosen Spring Boot/springdoc/Cucumber/Spotless versions with source URLs, generated files, test counts (JUnit and Cucumber separately), commands actually run, JAR and Docker verification results, Swagger URL, and remaining blockers. Mark each gate `PASS`, `FAIL`, or `NOT RUN`. **Only claim complete success when all mandatory local build and test gates have passed.**
